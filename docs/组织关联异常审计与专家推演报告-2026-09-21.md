# 组织关联异常审计与专家推演报告

- **日期**：2026-09-21
- **范围**：学校→级部→班级→老师/学生/家长 四级组织关联关系的逐行审计
- **方法**：主智能体逐行核查 + 三位专家（PM / 代码分析师 / 数据库专家）并行独立推演、交叉验证
- **结论**：用户实测的两个问题**均确认存在且根因明确**；另排查出 6+ 处同源/衍生关联异常。

---

## 一、总结论（问题确认）

| 用户反馈 | 结论 | 直接根因 |
|---------|------|---------|
| **问题1：级部无法挂到新学校** | ✅ 确认存在 | 写路径 `schoolId` 强制覆盖为登录校 + 全局超管被误锁在"演示学校" |
| **问题2：老师无法与级部关联** | ✅ 确认存在 | 系统无"老师↔级部"直接关系；间接路径（老师→班级→级部）断在"班级↔级部"环节——界面根本无法给班级挂级部 |

---

## 二、组织关联模型现状（全景）

| 实体 | 外键关联 | 唯一约束 | 关键字段 | 状态 |
|------|---------|---------|---------|------|
| School（学校） | 多租户根 | uk_school_code | code | 正常 |
| Level（级部） | school_id→School | uk_school_level(school_id,name) | school_id NOT NULL | 正常（写路径有缺陷） |
| ClassEntity（班级） | level_id→Level、school_id→School | uk_class_school_name(school_id,name) | **level_id/school_id 可空** | ⚠️ |
| Student（学生） | class_id→Class、school_id→School | uk_student_no | class_id/school_id | ⚠️ school_id 可空 |
| TeacherClass（老师-班级） | teacher_account_id→Account、class_id→Class | uk_teacher_class | 无 school/level 冗余 | ⚠️ 缺校级冗余 |
| Account（账号） | school_id→School | uk_username、uk_phone | scope_type/role | ⚠️ 超管 schoolId 非空 |
| Grade（成绩） | student/exam/course | uk_student_exam_course_source | **school_id 冗余快照可空** | ⚠️ 快照无约束 |
| Course/ExamType/Exam | school_id→School | 各 uk_school_name | school_id | 写路径有缺陷 |
| ParentStudentBind | parent→Account、student→Student | uk_parent_student | — | 正常 |

**设计语义**：老师对"级部"的归属是**间接**的（老师→班级→级部 level_id），系统**不存在** `teacher_level` 直接关系表/接口/界面。

## 三、逐条异常清单（按严重级别）

### P0-1 级部无法挂到新学校（用户问题1，确定性 bug）
- **证据**：`LevelService.create()`（L40-44）
  ```java
  Long sid = dataScopeService.currentSchoolId();   // = 登录用户 schoolId
  Long schoolId = (sid != null) ? sid : req.getSchoolId(); // 非空则丢弃请求体！
  ```
- **根因链**：`DataSeeder.java:236` 把全局超管 admin 设置 `schoolId=演示学校ID`（非空），于是 `currentSchoolId()` 恒非空 → 无论前端在下拉选哪个新学校，后端都用 `schoolId=演示学校` 强制覆盖 → 级部被建到演示学校，**新学校永远挂不上级部**。
- `LevelService.update()`（L63-64、L76-78）同款，**甚至会把已有他校级部重挂到演示学校**。

### P0-2 班级无法挂到级部（确定性 bug，衍生问题2的一半）
- **证据**：前端 `Dictionary.vue` 班级管理：新增/编辑班级对话框**只有 name 字段**，从不传 `levelId/schoolId`。
- 后端 `DictionaryService.createClass()`（L66-67、L87）：`schoolId` 强制为登录校（超管=演示学校）、`levelId=null` 写入。
- **后果**：全系统班级 `level_id` 恒为空，学校→级部→班级 链路在"班级↔级部"处彻底断裂。

### P0-3 老师无法与级部关联（用户问题2）
- 无 `teacher_level` 直接关系；老师对级部归属只能 `teacher_class → class.level_id` 间接推导。
- 因 P0-2 班级 `level_id` 为空，间接推导恒为 null → 老师实际无法关联任何级部。
- 前端"老师班级归属"（`Organization.vue` L51-87）只有班级维度，**无级部维度、无级部筛选入口**。

### P1-4 读路径把全局超管锁在"演示学校"（设计副作用，放大多校管理问题）
- 证据：`DictionaryService.listClasses()`（L56-57）、`listCourses()`、`listExamTypes()`、`AuthService.listTeachers()`（L240-243）均 `sid==null ? 全部 : findBySchoolId(sid)`。
- 因 admin `schoolId` 非空，超管**只看到演示学校**的班级/课程/考试类型/老师 → 老师绑定班级的下拉、词典页下拉都选不到新学校数据 → 无法为新学校老师配班级/级部。

### P1-5 课程/考试类型无法建到新学校（确定性 bug，同源）
- 证据：`DictionaryService.createCourse()`（L137 用 `requireLogin().getSchoolId()`，不回退请求体）、`createExamType()`（L179）。超管建课程/类型恒归演示学校。
- `updateCourse`（L150/153）、`updateExamType`（L195/198）在 admin 视角还会把"改新校数据"当作跨校而 403 拒绝。

### P1-6 全局超管识别条件错误（总根因）
- 证据：`DataScopeService.currentSchoolId()` 仅以 `schoolId==null` 判定"全局超管"，注释亦然；但 `DataSeeder` 给 admin 设了非空 schoolId → **SCOPE_ALL 超管从未被当作超管处理**，被当成"演示学校归属用户"，从而触发 P0-1/P0-2/P1-4/P1-5。

### P2-7 前端组织树拆散、无统一视图
- `Organization.vue`：学校/级部/老师；`Dictionary.vue`：班级/课程/考试类型；学生另在 StudentList。四级组织分处多页、无联动树，跨页拼接易遗漏挂接；级部新增后下拉不自动切换到新学校（`loadSchools` 不重置 `levelSchoolId`）。

### P2-8 级联删除缺口（数据库层）
- `DictionaryService.deleteClass()` 只校验学生，**不清理 teacher_class 关联** → 删班后 class_id 悬空成孤儿；也未清 grade。
- `SchoolService.assertNoDependencies()` 未校验 `exam_course_group` → 仅含科目的学校删除时漏检。
- （`LevelService.delete` 校验班级、`AuthService.deleteTeacher` 清理 teacher_class 均完整。）

### P2-9 数据模型缺口（数据库层）
- `ClassEntity.school_id`/`level_id` 可空且**不校验与 level.school_id 一致** → 班级可与级部不同校（分裂）。
- `Grade.school_id` 为**可空冗余快照、非 NOT NULL、无 DB 约束** → 写路径回填缺漏即产生 NULL/错校孤儿成绩，按校聚合漏算/串算（DB 专家判定为"高"风险）。
- `teacher_class` 缺 `school_id/level_id` 冗余列 → "某校/某级部全部老师"需三表 JOIN 且无穷层防线，越权仅靠服务层业务校验兜底。

## 四、修复方案建议（分优先级，供确认后落地）

### P0-修复（治本，先做）
1. **修正全局超管识别**：`DataScopeService.currentSchoolId()` 及所有 `B4` 写路径强制逻辑，改为**同时识别 `scopeType=ALL`（全局超管）**——超管时可显式指定/信任请求体 `schoolId`；仅带归属校的普通老师（SCHOOL/CLASS 且 schoolId 非空）才强制用登录校。**（改动：DataScopeService、LevelService、DictionaryService、AuthService）**
2. **`LevelService.create/update`**：超管信任请求体 `schoolId` 并校验其存在；普通老师锁定登录校。
3. **`DictionaryService.createClass/updateClass/createCourse/createExamType`**：对齐上述口径。

### P0-前端（配套）
4. `Dictionary.vue` 班级管理对话框**增加"学校 + 级部"下拉并传 `schoolId/levelId`**；`loadClasses` 按选中学校刷新。
5. `Organization.vue` 级部新增后**将 `levelSchoolId` 切换到新学校**；"级部管理 / 老师绑定"的班级下拉**按学校过滤**。

### P1（体验完善）
6. 前端统一组织树或班级管理入口：把学校→级部→班级→老师挂接集中一处，或至少在"老师班级归属"增加**级部维度筛选**。

### P2（数据层加固）
7. `ClassEntity.school_id` 设 NOT NULL 并校验与 `level.school_id` 一致；`Grade.school_id` 写时强制回填并加约束；`teacher_class` 增加 `school_id` 冗余列。
8. 补级联清理：`deleteClass` 清理 teacher_class/grade；`assertNoDependencies` 补查 exam_course_group。

> 说明：删除类修复涉及 JPA `ddl-auto` 建表，需与《个人版校园版-统一数据库字段规范-第六轮DDL基线.md》对齐后再动。

## 五、专家推演结论汇总（三方交叉验证一致）

- **代码分析师**：逐行确认 P0-1/P0-2/P1-5 为**确定性 bug**，P1-4 为**设计副作用**；总根因在 `currentSchoolId()` 以 `schoolId==null` 判定超管、而 admin 实际 schoolId 非空。
- **PM**：判定"级部下拉是假入口"（前端让用户选校但后端强制登录校）与"班级无法挂级部"为问题1、问题2 的产品层直接成因；无 `teacher↔level` 直接入口。
- **数据库专家**：判定数据模型整体外键/唯一约束合规；最大缺口在 `Grade.school_id` 可空快照、`class.school_id` 与 `level.school_id` 无一致性约束、`teacher_class` 缺校级冗余、删除级联缺口。

三方结论与主智能体逐行核查完全一致，无分叉。
