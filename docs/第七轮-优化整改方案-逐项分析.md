## 一、P0 · 唯一致命短板（安全，先做）

### I-1 内存 token 会话化（★）

**根因**
`AuthService` 使用进程内 `ConcurrentHashMap<String, Long> sessions` 存 `token→accountId`。会话：
- 重启即全部失效（所有用户被迫重新登录）；
- 无过期时间（token 永久有效）；
- 无集中失效/踢人能力；
- 多实例部署时各实例互不可见（session 不共享）。
根因是**会话状态存于无状态应用进程内**，属设计选型遗留（v5 认可"单机可接受"）。

**影响范围**
全站鉴权链路：`AuthService.findByToken` ← 全局拦截器/`LoginUserContext` ← 所有需登录接口。影响所有角色（老师/家长/管理员）。单机演示可运行，但**多实例、灰度、重启、安全审计均受阻**。

**改进目标**
把会话凭证从"进程内内存"迁移为**可持久化、可过期、可集中失效**的无状态/半无状态模型，同时保持现有 `X-Token` 前端契约不变（前端零改动或最小改动）。

**优化方案（两选一，推荐 B）**
- **方案 A：Redis 集中会话**。`sessions` 改为 Redis（`key=tk:{token} → accountId`，TTL=30min 滑动续期）。
  - 改动：`AuthService` 注入 RedisTemplate/StringRedisTemplate；`login` 写、`findByToken` 读、`logout` 删、滑动续期用 `expire`。
  - 优点：可集中踢人、可精确过期、多实例共享；失败锁定也可下沉 Redis（`INCR`+`EXPIRE`）。
  - 成本：引入 Redis 依赖与部署组件。
- **方案 B：JWT 无状态签名令牌（推荐）**。
  - `login` 签发 `HMAC-SHA256` 签名 JWT（`jwt.io`/`jjwt`），payload 含 `accountId/role/nickname/schoolId/scopeType` + `exp`（如 24h）+ `iat`。
  - `findByToken` 改为**验签 + 校验 exp**，不再查库（无状态、天然分布式无共享）。
  - 失效方式：采用**短 TTL + 黑名单**（`blacklist:{jti}` 存 Redis，logout/改密/踢人时加入；TTL=原 token 剩余），兼顾无状态与可控失效。
  - 前端契约：header 仍叫 `X-Token`，内容换成 JWT 串，**前端几乎零改动**（仅 logout 需服务端黑名单 + `exp` 未到前客户端可主动删 localStorage）。
  - 优点：无 Redis 也可承载（纯内存黑名单兜底单机），分布式天然可扩展。
  - 成本：引入 `jjwt` 依赖；需处理黑名单存储。

**预期效果**
- 重启不再全量掉线；token 有明确过期；可集中踢人/改密后失效；多实例无共享问题。
- 安全强度显著提升，满足"集中失效 + 过期"两大审计要求。

**潜在风险**
- **JWT 一旦签发，改密前旧 token 仍有效**（除非配黑名单）——须把"改密/重置密码/解绑/注销"事件写入黑名单，否则是安全回退点。
- 引入依赖与密钥管理（`HS256` 密钥需外置配置/环境变量，不能硬编码）。
- 若选 Redis：增加运维组件；Redis 故障时需降级策略（可接受短暂集中登录失败）。
- 前端：若采用"服务端黑名单含 exp"，需处理网络异常时的一致性（建议前端成功收到 401 才清 token）。

### I-2 localStorage token XSS（★）

**根因**
`frontend/src/api/http.js` 从 `localStorage.getItem('auth')` 读取 token，注入 `X-Token`；`utils`/`useAuth` 亦读写 localStorage。一旦页面被注入任意 JS（XSS），攻击者可直接读走全部登录态，**凭证完全暴露**。根因是**凭证存放于可被脚本读取的同源存储**，且 `http.js` 对可能含 `<`/`>`/引号 的用户输入未统一转义。

**影响范围**
所有浏览器端用户；若结合存储型 XSS（如录入姓名/课程名中含 HTML），可窃取任意登录用户 token 冒充操作。为**全站安全致命点**（公网上线必改）。

**改进目标**
凭证默认**不可被脚本读取**（HttpOnly Cookie），或至少将当前暴露面收敛 + 缓释（输入转义 + CSP）。

**优化方案（推荐 A 为主，B/C 兜底）**
- **方案 A：HttpOnly Cookie 承载凭证（根治）**。
  - `login` 由服务端 `Set-Cookie: SESSION=<token>; HttpOnly; SameSite=Lax; Path=/; Secure(生产)`。
  - 前端 `http.js` 去掉 `X-Token` header 注入，改为 `withCredentials: true`（axios）走 Cookie 自动携带。
  - 后端加 `CORS` 配置（同源部署可不开）；`Logout` 服务端清 Cookie。
  - 效果：token 脱离 JS 可读范围，XSS 拿不到会话。
- **方案 B：CSP 头（Content-Security-Policy）**。后端/网关对所有响应加 `Content-Security-Policy: default-src 'self'; script-src 'self'` 等，限制脚本加载来源，从源头压制 XSS 注入面。
- **方案 C（无论 A/B 都要做）**：所有后端校验仍要**服务端校验权限**（本来就做），前端对用户可控文本渲染用 Vue 插值（默认转义），不滥用 `v-html`。

**预期效果**
- XSS 无法再读取会话凭证（HttpOnly Cookie），配合 CSP 显著降低注入成功率；即使有存储型 XSS 突破点，登录态也不外泄。
- 与 I-1（JWT/会话）叠加构成完整安全闭环。

**潜在风险**
- **Cookie 有 CSRF 面**（浏览器自动携带）：需给写操作加 CSRF 防护（双提交 Cookie / CSRF Token / 校验 `Origin`+`SameSite=Lax`）。`SameSite=Lax` 已能缓解大部分 GET/跨站，但 POST 仍需 Origin 校验。
- 跨域部署（前后端分域）时 Cookie 需 `SameSite=None; Secure` + 精确 `allowedOrigins`，配置更严；同源单 jar 部署最省事。
- 兼容性：HttpOnly+Secure 需 HTTPS 才能携 Cookie（本地 http 开发可用 `Secure` 关闭或本地 http 豁免，注意生产必须开启）。
- 迁移影响现有登录/登出流程，需回归 AuthFlow 测试。

## 二、P1 · 权限全链（老师 DataScope + 跨校一致）

### I-3 老师写操作班域校验 + comparison 级部过滤（▲）

**根因**
- `GradeService` 老师分支的 `ensureManageable` 只校验"是否 teacher 来源"，**未校验该成绩归属班级是否在当前老师 `teacher_class` 数据范围内** → 越权写入/删除他人班级成绩。
- `StatisticsService.comparison`（班级对比）目前按全部班级聚合，老师查看时**未按 DataScope（teacher_class→可见班级/级部）过滤** → 超范围数据泄露。
根因是 **`teacher_class` 基建（种子/界面/接口）在本轮才补齐，而写操作与 comparison 两条消费链尚未接入 DataScopeService**。

**影响范围**
老师端成绩录入/改删、班级对比报表。属多租户权限全链的**漏网支路**，若不修，老师可越权篡改/查看非管辖班级数据，破坏隔离语义。

**改进目标**
使**所有老师可见/可写数据统一收敛到 DataScopeService 判定的可见范围**（class/level/school 三级），与现有排名/学生列表的过滤口径一致。

**优化方案**
1. **写操作校验**：`GradeService.ensureManageable`（老师分支）追加——待操作成绩所属 `Student.classId` 必须落在当前老师可见班级集合内（`dataScopeService.requireVisibleClassIds(user)` 或 `isClassVisible(user, classId)` 判定），否则 403。
2. **comparison 过滤**：`StatisticsService.comparison` 老师分支在聚合前，用 `dataScopeService.extendVisibleClassFilter(...)`（或注入 `visibleClassIds`）把班级集限制到老师可见范围；沿用 ranking 已实现的 `requireAnyVisibleClass` 判定（无可见班级 → 返回空并提示）。
3. **测试**：`SchoolLevelMultiTenantTest` 或新增用例——老师 A 只绑 1 班，改/删 2 班成绩应 403；comparison 只返回可见班级。

**预期效果**
- 老师可见/可写范围与数据范围完全一致，杜绝越权；comparison 报表不再泄露他班数据。
- 与排名/学生列表口径统一，隔离语义自洽。

**潜在风险**
- 需在 `teacher_class` 有真实绑定数据的前提下才有效；若某老师无任何绑定，会从"全部"退化为"空"——这是期望行为（等同 `requireAnyVisibleClass` 拦截），但要确保提示友好、不误伤演示数据（种子须为老师预置绑定）。
- performance：每次写操作多一次班级可见查询，量小可忽略。
- 改动集中但横跨 GradeService / StatisticsService / DataScopeService，需回归全部测试（51 项）。

### I-4 teacher-classes 跨校一致性校验（▲）

**根因**
`TeacherClassService.assign(TeacherClassAssignRequest{teacherAccountId, classIds})` 目前直接落 `teacher_class` 行，**未校验被绑班级 `ClassEntity.schoolId` 与老师 `Account.schoolId` 是否属同一学校**（也可能未限制老师本身有无 schoolId）。根因是**绑定粒度只看 id，未做多租户一致性断言**。

**影响范围**
组织管理 `teacher-classes` 归属绑定。若跨校错绑，老师数据范围会串到其他学校班级，破坏多租户隔离。

**改进目标**
在服务层保证 **老师所属学校 = 所绑班级所属学校**，跨校绑定一律拒绝。

**优化方案**
- `TeacherClassService.assign` 内逐 classId：取 `ClassEntity`（校验存在且未删），断言 `class.getSchoolId().equals(teacher.getSchoolId())`；任一不符则抛 `BizException(400,"不能跨学校绑定班级")`（或整体回滚）。
- 老师 `Account.schoolId` 为空时，用其可见学校默认（或要求先归属）。
- 测试：`SchoolLevelMultiTenantTest` 补"绑定他校班级 → 拒绝"用例。

**预期效果**
- 从数据入口杜绝跨校错绑，多租户隔离在归属绑定环节闭环。

**潜在风险**
- `teacher_class` 现有种子/历史数据若存在跨污点，需先清洗（本轮种子是同校，无碍）。
- 老师 schoolId 缺失情况需明确策略，否则误拦合法绑定。

## 三、P1 · 数据正确性与性能

### I-6 findByStudentIdIn 下沉 source + avg 聚合索引（▲）

**根因**
- `GradeRepository.findByStudentIdIn(ids)` 按"绑定学生集"全量拉取再在内存过滤 source，未把 `source` 条件下沉 SQL → 家长查询量大、无索引利用。
- `avg(score)` 聚合在 `scores()/stats()` 无 `(course_id, source)` 覆盖聚合索引 → 大表下聚合慢。
根因是**查询条件未下沉 + 缺针对性复合索引**。

**影响范围**
家长端成绩列表、统计聚合（成绩查询/统计/进度）。数据量大时影响明显。

**改进目标**
把过滤/聚合下沉到 DB，并为高频聚合路径建索引，减少内存过滤与全表扫描。

**优化方案**
1. 新增派生方法 `findByStudentIdInAndSource(ids, source)`（含 `source='teacher' or 'parent'`），或改 `findByStudentIdIn` 走 JPQL 带 source 条件；`GradeService.list` 家长分支改用之，去掉内存 `.filter`。
2. DDL 基线/实体索引新增：`idx_grade_course_source`（已有 `(course_id,source)`）基础上，为聚合路径补 `(course_id, source, exam_id)` 或直接评审成果——明确 avg 需覆盖 `course_id+source(+exam_id)`。同步 `@Table(indexes=...)` 与 DDL 文档一致。
3. 若走 PG profile 实测 `EXPLAIN` 验证索引被命中。

**预期效果**
- 家长列表/统计 SQL 带 source 过滤且命中索引，响应与吞吐提升（数据集大时尤为明显），并为生产 PG 打底。

**潜在风险**
- 索引增多会略增写入开销（可接受）。
- 派生方法名与既有 `findByStudentIdIn` 并存需测试覆盖；改查询语义（原来返回 teacher+parent 两源）须确保家长看到的集合不变（仍=teacher+parent）。

### I-7 DataSeeder 事务化/幂等跳闸（▲）

**根因**
`DataSeeder` 在应用启动 `CommandLineRunner`/`ApplicationRunner` 直接 `save`，**无整体事务包裹、无"已播种则跳过"的幂等闸** → 重复启动可能重复播种或部分失败留下半种子。

**影响范围**
开发/演示环境启动稳定性；生产若误用会导致数据污染。

**改进目标**
播种整体事务化 + 幂等（已有数据则跳过），避免重复/半量种子。

**优化方案**
- 播种方法加 `@Transactional`（或 `ApplicationRunner` 内的 `TransactionTemplate.execute`），任一失败整体回滚。
- 幂等闸：已存在 `school.code='DEFAULT'`（或约定标识）等探针记录则整个跳过；或各表先 `existsBy...` 再插。
- 可选：用 `@Profile` 或配置开关 `app.seed.enabled` 控制生产是否播种。

**预期效果**
- 任意次启动均幂等、原子；生产环境可显式关闭播种。

**潜在风险**
- 幂等探针要稳定（按唯一键判定），否则误跳过新种子版本升级；建议探针带版本号字段（`DEFAULT_V1` 等）。

## 四、P2 · 代码结构与测试

### I-8 StatisticsService 拆分（▲）

**根因**
`StatisticsService` 承载 course / student(多科) / student-trend / comparison / rank / progress / semester 等多职责 → 单类体积大、内聚低、难维护难测试。根因是**缺乏按领域切分**。

**影响范围**
后端可维护性/可测性；后续新增统计口径时冲突面大。

**改进目标**
按"单一职责"拆成若干专注服务，保持现有 Controller 契约与返回结构不变（对外零破坏）。

**优化方案（推荐拆法）**
- `StatisticsFacade`（门面，Controller 仍注入它，转调下层）或直接每个 Controller 注入对应服务：
  - `CourseStatService`：course
  - `StudentStatService`：student（多科总分）、student-trend、progress
  - `CompareStatService`：comparison
  - `RankStatService`：ranking
  - `SemesterService`：semesters
- 公共逻辑（DataScope、得分率/标准分/三口径计算、班级名映射）下沉 `StatSupport`/`StatCalc` 工具或基类。

**预期效果**
- 单类职责清晰、单元可测（可拆出纯计算 `StatCalc` 做无 Spring 依赖的单测）、后续扩展成本低。

**潜在风险**
- 拆分类多、Controller 注入点调整，需回归全部统计测试（StatisticsMetricTest/ParentRankPrivacy/SettingsAndAnalysis）验证契约不破。
- 过度拆分反增样板，需克制：按"计算纯函数可独立测试"为界。

### I-9 前端组件级/集成测试补齐（▲）

**根因**
当前前端单测仅覆盖路由守卫等少量纯逻辑（`resolveNav`），组件级（`@vue/test-utils` 挂载 + mock api）与集成链路测试缺失。根因是**测试投入仅覆盖了最易测的纯函数**。

**影响范围**
前端回归保障弱；新增页面/接口（如本次 Statistics 学生总分、Organization）无自动化护栏。

**改进目标**
补齐"关键页面组件 + 关键交互"的组件级测试，并覆盖新联调点，形成前端质量门禁。

**优化方案**
- 用 `@vue/test-utils` + `vi.mock('../api')` 为 `Statistics.vue`（学生总分四口径渲染）、`Organization.vue`（学校/级部/老师-班级 CRUD 交互）、`Login.vue`、`ParentBind.vue` 各写 1–3 个冒烟用例（渲染 + 关键 onMounted 请求 + 关键按钮回调）。
- 抽 `useAuth`/`api` 为可 mock 边界；对网络层统一 mock。
- 将单测纳入 `npm test`（已配 vitest）并作为 `npm run build` 前的门禁（build 脚本 pre 钩子或 CI）。

**预期效果**
- 关键页面渲染与交互有护栏；重构/新增联调点出现回归能即时捕获。

**潜在风险**
- 组件测试需 mock ECharts/ElementPlus 全局组件（`plugins`/`global.stubs`），配置成本中等；需以少量高价值用例起步避免过度。

### I-11 studentTrend 批量入口（▲）

**根因**
第五轮遗留：`StudentTrend.vue` 个人趋势仅"单学生逐次查看"，无批量/列表入口。根因是**交互入口未做，非后端缺失**（后端 `/student-trend` 单生接口已在）。

**影响范围**
老师端"个人成绩趋势"可用性/效率。

**改进目标**
提供"学生列表 → 点击进入个人趋势"的批量入口，降低逐个输入学号成本。

**优化方案**
- 在学生列表/趋势页顶部加可选学生下拉或列表（复用 `studentApi.list`），选中即触发趋势加载；或从成绩查询行提供"看趋势"跳转。
- 无线业务改动，纯前端入口增强。

**预期效果**
- 老师查看多生趋势路径缩短，操作效率提升。

**潜在风险**
- 低（纯 UI 入口）；注意学生量大时下拉用 `filterable` + 远程搜索。

## 五、P2/P3 · 配置化与低危项

### I-10 magic number 配置化（▲，可维持）

**根因/范围**
`AuthService.MAX_FAIL=5`、`LOCK_MS=15min` 硬编码。v5 已明确确认"不配置化"（考虑双父母与策略审慎）。

**改进目标/取舍**
- **建议维持硬编码**（与 v5 结论一致），但把常量收敛到 `AuthService` 顶部集中注释说明意图 + 可将来切换到 `@ConfigurationProperties`。
- 若后续要配置化：新增 `security.login.maxFail/lockMinutes` 绑定到 application.yml，注入方式改为构造入参，测试覆盖默认值。

**预期效果**
不改变行为；降低将来调整阈值成本。**潜在风险**：很低（保持现状即零风险；若配置化需防覆盖导致锁定失守）。

### I-13 BCrypt 盐字段区分（○，可维持）

**根因/范围**
`id_card_hash` 用 BCrypt（自带盐），内部使用为脱敏而非校验密码，无需单列盐字段。

**改进目标/取舍**
- **建议维持现状**并在代码注释说明（BCrypt 盐内嵌于哈希串，无需单独 salt 列；`id_card_hash` 仅用于"不可逆比对"）。
- 不新增字段（避免 DDL 与既有基线不一致）。

**预期效果 / 风险**
维持现状零收益差、零风险；若强行加盐字段将破坏 DDL 基线一致性，得不偿失。

## 六、P3 · 前端/产品（C 类，产品排期）

### I-12 侧边/统计页臃肿 + C 类产品功能（○）

**根因/范围**
侧边栏随功能增长变长；`Statistics.vue` 用 Tabs 承载 6 个分析视图趋臃肿；且 C 类产品功能（单学生档案页、批量导入、消息通知、报表分享、知识点题型、管理员/查看者角色）未实现——属**产品待办**而非缺陷。

**改进目标/取舍**
- **信息架构**：侧边栏按"数据/录入/分析/系统"分组或二级菜单；`Statistics.vue` 拆分到独立路由页面（分析中心）减少单页 Tab 压力——纯前端结构优化。
- **C 类功能**：建独立「产品待办」清单（附优先级/验收用例），与本次技术整改解耦，不进技术迭代主链，避免范围蔓延。其中「单学生档案页」可复用既有的 `student-trend`+`见详情`能力低成本增量实现。

**预期效果**
- 导航与统计页更清晰；C 类功能在专门清单下有序推进。
- **潜在风险**：低；拆页需同步路由与菜单权限（roles 校验已有）。
