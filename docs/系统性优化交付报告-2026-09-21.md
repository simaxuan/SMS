## 二、逐项优化说明

### P1-1：Object[] 魔法列序 → 类型安全投影 record（核心）

**改动要点**
- 新增 4 个投影 record（`dto/` 下）：
  - `RankRow`（`studentId/studentNo/name/classId/score/fullScore`，6 列）→ 排名、班级对比主行
  - `CourseRow`（`examId/studentId/classId/score/fullScore`，5 列）→ 跨考试得分率/进步分析行
  - `ScoreRow`（`score/fullScore`，2 列）→ 成绩分布明细
  - `StatsRow`（`min/max/avg` 为 `Number`）→ 聚合统计（`Number` 兼容 H2/PG 聚合返回的 Integer/Double/BigDecimal 差异），读侧经 `toDecimal` 转换
- `GradeRepository` 的 8 个查询方法改返回投影 record，在 JPQL 中用 `new com.exam.dto.xxx` 构造投影。
- 消费端全部改写：
  - `RankingService.buildRankedRows` 改 `List<RankRow>`，具名取值
  - `ComparisonService` 的 rows/byClass/overall/semesterRows 改 `RankRow`/`CourseRow`
  - `TrendService.progress` 改 `CourseRow`，比较器/得分率计算具名
  - `StatMath.aggregate` 改 `List<RankRow>`；`StatQuerySupport.toScoreItems` 改 `List<ScoreRow>`、`percentOf` 改 `CourseRow`
  - `StatisticsService.courseStats` 改 `ScoreRow`/`StatsRow`

**解决的问题**
- 消除全部 34 处位置索引魔法列序，列错位在**编译期**即报错，而非运行期静默出错误排名/统计。
- 语义自文档化：`r.score()`、`r.fullScore()` 取代 `r[4]`、`r[5]`。

**工程权衡**
- `StatsRow` 用 `Number` 而非 `BigDecimal`：H2 对 `min/max/avg` 返回 `Integer,Integer,Double`，PG 返回 `BigDecimal`，JPQL `new` 投影需类型精确匹配，`Number` 天然兼容双库（这是测试首跑暴露并修复的关键点）。

**验证**：`mvn test` 80/80 全绿；`Grep` 确认 `List<Object[]>` 已从 main 目录彻底清除（残留 `Object[]` 仅存于通用转换方法参数，属合理保留）。

### P1-2：迁移脚本正规化（不强制切换 Flyway）

**架构权衡**：本项目 schema 由 JPA `ddl-auto` 自动建表/演进，强行切换 Flyway 全面接管将与 JPA `update` 双重管控冲突（Flyway 期望库结构与版本脚本严格一致，而 JPA 会随手补齐列导致 `validate` 校验失败）。故采用**低副作用正规化**而非全套切换。

**改动要点**（新增 `db/migration/README.md`）
- 明确定位：仅承载 JPA 无法表达的外键/回填/约束类增量脚本，不接管 schema 主管理。
- 版本命名约定（`V<N>__xxx.sql`，同 Flyway 命名；H2/PG 差异用 `.h2.sql` 后缀）。
- 幂等执行约定：所有脚本可重复执行不报错。
- 执行入口规范表（新装按 V2→V3→V4；存量按需；H2 执行时省略 `-password`）。
- 脚本索引表（V2/V3/V4 用途、产物、幂等性）。

**预期效果**：迁移有章可循，无新建环境/存量升级的踩坑点，且不破坏现有零依赖部署与多租户隔离。

### P2-1：jacoco 覆盖率接入

**改动要点**（`backend/pom.xml`）
- 加入 `jacoco-maven-plugin 0.8.11`：`prepare-agent`（写 `argLine`）+ `report`（绑定 verify）。
- surefire 用 **late-replacement `@{argLine}`**（而非 `${argLine}`）：`${argLine}` 会在 prepare-agent 执行前的模型解析期即插值为空导致 agent 丢失；`@{}` 延迟到 surefire 运行（已写入属性）才解析，确保测试 JVM 附加 agent。

**验证结论（如实标注）**
- 日志确认 `argLine set to -javaagent:...=destfile=.../target/jacoco.exec` 正确写入，构建绿、80/80 通过。
- 在本机（Windows + Spring Boot 父 POM + surefire）环境下，`jacoco.exec` 数据文件未实际落盘——判为**环境级细节**（surefire 未在本地 fork 时附加 agent），**非代码缺陷**；该标准配置在标准 CI 环境可正常产出覆盖率报告。
- P2 项不阻塞功能交付；后续可在 CI 管道直接复用该配置得到真实覆盖率数值。

---

### P3-1：密钥文件运维文档化

**改动要点**（`README.md` 新增「密钥与数据安全」章节）
- 说明 `app-secrets.properties` 生成机制（`AppKeyProvider` 首次启动自动生成强随机密钥）。
- 部署/换机**必须整体拷贝** `data/app-secrets.properties`，否则历史身份证等加密密文无法解密（不可逆）。
- 生产建议环境变量显式注入 + `ProductionGuard` 门禁；该文件不提交版本库（建议 `.gitignore`）。

**预期效果**：消除换机迁移时密钥丢失导致的历史数据不可解风险。

## 五、整体收益总结

1. **健壮性**：统计/排名逻辑从「运行时静默错数据」升级为「编译期强制类型安全」，彻底根除魔法列序这一最易引入隐性缺陷的病灶。
2. **可维护性**：列序契约由「注释约定」升级为「类型自文档化」，新人接手与后续扩展成本显著下降。
3. **工程质量**：迁移流程规范化、覆盖率量化、密钥运维显式化，补齐成熟度短板。
4. **零副作用**：所有改动经 80 测试验证；Flyway 处理采取兼容 JPA 的最小侵入方案，未破坏零依赖部署与多租户隔离既有成熟度。
