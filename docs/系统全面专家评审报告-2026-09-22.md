# 系统全面专家评审报告（2026-09-22）

## 一、评审方法

- **评审对象**：「成绩分析系统」全栈（Spring Boot 3.2.5 + Java 21 + JPA\[H2/PG\] 后端；Vue3 + Vite + Element Plus + Pinia + Axios + ECharts 前端；多租户=单库 school_id 逻辑隔离；publish.ps1 单 jar+启动器 exe+精简 JRE 零依赖打包）。
- **参与视角**：① 后端架构/技术实现/代码质量/可维护性；② 性能与安全性；③ 需求覆盖度/业务逻辑；④ 前端体验与工程化。
- **评审方式**：只读、证据化（引用 文件:行 / 文档:节），先各视角独立发表意见，再按统一维度打分汇总。
- **统一评分维度（各 0–100）与权重**：
  | 维度 | 权重 |
  |---|---|
  | ① 功能完整性 | 20% |
  | ② 需求覆盖度 | 15% |
  | ③ 代码健壮性 | 15% |
  | ④ 可扩展性/架构合理性 | 10% |
  | ⑤ 性能与安全性 | 20% |
  | ⑥ 可维护性与文档·易用性 | 20% |
- **严重度**：P0 阻断 / P1 重要 / P2 一般。**优先级**：高 / 中 / 低。
- **总分** = Σ(维度分 × 权重)。

## 二、各视角意见

### E1 后端架构·代码质量·可维护性
- **亮点**：分层清晰（Controller/Service/Entity/Repository/Common/Config）；多租户隔离收敛到 `DataScopeService`（`resolveWriteSchoolId`/`effectiveSchoolId`/`schoolFilterForStatistics`/`isGlobalAdmin`，L64–176）单一权威层，口径统一、注释详尽；`GlobalExceptionHandler`（L31–61）统一业务/校验/系统异常并带 MDC traceId/uid/uri；`R<T>` 响应封装统一；全库**无空捕获异常**（Grep 空 catch=0），杜绝静默吞错。
- **问题**：
  - P1 健壮性：多处 `findById().get()` 直取 Optional（`AuthService`/`ParentService` 等，service 层 12 处 `.get()`），父记录缺失依赖前置校验，数据异常时抛 `NoSuchElementException`→500，建议统一 `orElseThrow` 转 404（评审基础：Grep `.get()` 分布）。
  - P2 认知负担：`RevocationStore` 存在两套实现（`JpaRevocationStore` 为唯一 Bean 生效、`InMemoryRevocationStore` 降为参考），职责边界依赖注释说明，建议清理参考实现或进一步封装接口以减少双实现心智成本。

### E2 性能与安全性
- **亮点**：鉴权闭环扎实（JWT uid/ver/jti + `AuthInterceptor` 逐请求解令牌重取数据库 schoolId；`exam_token` HttpOnly+SameSite=Lax 防 XSS 窃取；失败锁定 5 次/15 分钟；AES 加密 idCard + `WRITE_ONLY` 防序列化泄漏）；越权防护完善（读路径 `effectiveSchoolId` 强校验同校消除 IDOR、写路径 `resolveWriteSchoolId` 不信任请求体、`createClass` 空归属校拦截）；`Grade@Version` 乐观锁 + 唯一约束冲突转 409；V3 物理外键 24 条 + 索引已落地并对 H2 双库实测（孤儿插入被 `FK_STUDENT_CLASS` 拒绝）。
- **问题**：
  - P1 部署安全：JWT 密钥与 AES 密钥提供了**内嵌默认值**（`application.yml` token-secret 默认、`AesCrypto` 默认 key），`ProductionGuard` 已告警；若生产误用默认值上线，存在令牌伪造/密文可解风险（评审基础：ProductionGuard 启动告警 + config 默认值）。上线必须环境变量注入。
  - P1 性能：统计/排名类聚合对**内存集合过滤**（如 `DataScopeService.filterGradeRowsByClass` L114–127 对 `Object[]` 行内存过滤、`visibleClassIds` 全量取班级），大数据量/全校时开销随数据线性增长；H2 文件库为单机部署，高并发多校并发统计存在放大。建议库层分页/条件下推、必要时索引/物化口径。
  - P2 集群一致性：`InMemoryRevocationStore` 的失败计数等状态内存态，水平扩展多实例不共享；当前单机部署可接受，横向扩容需替换为共享存储（JpaRevocationStore 已覆盖 TV/DENY 持久化）。

### E3 需求覆盖度·业务逻辑
- **亮点**：与基线文档高度对齐（`docs/个人版校园版-统一数据库字段规范-第六轮DDL基线.md`、v5 定稿、多租户隔离口径）；隔离口径（SCOPE_ALL 带登录校收敛 / true-global schoolId=null 放开、admin true-global）已在代码+数据库双落地并 80 测试全绿；删除安全网（deleteClass 清 teacher_class、ExamService.delete 清 ECG、SchoolService 校验 system_setting 等）齐备。
- **问题**：
  - P2 占位功能：微信登录为**明确占位**（`AuthController:151-155`、`AuthService:360-362` 抛「尚未启用」），属既定范围外；若前端暴露微信登录入口需同步隐藏，避免「有按钮无能力」。
  - P2 未接线排查：文档与实际实现的版本同名易混淆（docs 存在多轮「覆盖率/评审」命名的同类报告），评审建议以「统一数据库字段规范-第六轮DDL基线」为准核对新字段，避免以旧文档误判。

### E4 前端体验与工程化
- **亮点**：既有 UI 专项已优化统计图颜色语义（涨绿/跌红）、App.vue 对话框响应式（max-width:92vw）、Dashboard 卡片 loading、成绩查询/录入 el-empty 空态、登录卡片窄屏适配；Element Plus 组件体系一致、ECharts 按需引入。
- **问题**：
  - P1 性能：前端依赖/构建产物偏重（node_modules 超万文件、vite 构建 2342 模块），首屏与资源体积存在优化空间，建议 Element Plus/路由级按需与拆包、静态资源压缩。
  - P2 一致性/易用性：缺统一全局错误 toast 约定（各页零散 alert/Message 混用）、loading 态未全量覆盖、响应式对窄屏表格的横向滚动与可访问性可再打磨。

## 五、改进建议（按优先级）

**短期（高优先）**
1. 上线安全基线：强制环境变量注入 JWT/AES 密钥，`prod` profile 对默认密钥 fail-fast。
2. 统计/聚合性能：把全校统计从内存过滤下沉为库层聚合/分页，固化解包 `.get()` 防御。
3. 前端拆包与按需引入，降低首屏与产物体积。

**中期（中优先）**
4. 收敛 `RevocationStore` 双实现；跨校切换改为会话级上下文（不再把 school_id 写库为账号归属）。
5. 统一前端错误 toast/loading/空态组件与全局约定。

**长期（低优先）**
6. 微信登录产品化（或明确下线前端入口）；生成 OpenAPI 契约文档；按「版本号+日期」统一归档评审/交付报告，避免同名混叠。

## 六、总体结论

系统在**功能完整、需求覆盖、安全隔离**三个维度属强项：多租户口径（SCOPE_ALL 收敛/true-global）代码+数据库全落地、24 条物理外键实测生效、越权/加密/锁定闭环、80 测试全绿、文档与交付流程成熟（84.4/100）。主要短板集中在**性能（H2 单机 + 内存过滤）**与**部署密钥默认值风险**，其次是少量可选型解包守卫与前端打包体积。**无 P0 阻断项**，综合评级为「良好偏优」，建议按「短期安全+性能基线 → 中期架构收敛 → 长期产品化与文档规范化」路径持续打磨。
