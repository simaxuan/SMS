### 各模块核心佐证（逐行取证摘录）

**① 后端业务层 — `GradeService.java`**
- 唯一键冲突两层兜底：`existsBy...` 预检 + `DataIntegrityViolationException` 转 409（L104-108、L142-144）；并发下 TOCTOU 竞态被唯一约束兜底。
- 乐观锁：`ObjectOptimisticLockingFailureException` → 409「已被其他操作更新，请刷新重试」（L145-147），杜绝静默覆盖。
- 批量录入宽容策略：逐行记录 skippedDetails（studentId/examId/courseId/reason），超满分/已存在/并发冲突均不中断、不静默丢失（L165-198）。
- 权限：老师 `ensureTeacherClassScope`（班域 + canManageClass）、家长 `ensureBound`（绑定校验）；改挂学生时对**新学生**重新校验（L119-127），防跨绑定/跨班越权。

**② 数据模型 — `Grade.java` / `Student.java` / `Account.java` / `DataScopeService.java`**
- 索引与唯一约束详尽：Grade 含乐观锁 `@Version`、`uk_student_exam_course_source` 唯一键、4 个索引。
- 敏感字段纵深防护：`Student.idCard` 用 `@JsonProperty(WRITE_ONLY)`、`idCardHash` 用 `@JsonIgnore`（L51-58）；`Account.passwordHash` 用 `@JsonIgnore`（L40）。**身份证密文/摘要/密码哈希绝不出现在任何 JSON 输出**。
- 多租户中央方法：`resolveWriteSchoolId`（写路径锁定登录校，仅 true-global 信任请求体）、`effectiveSchoolId`（读路径收敛）、`schoolFilterForStatistics`（统计 SQL 下推兜底）、`visibleClassIds/canManageClass/requireAnyVisibleClass`（班域）——统一隔离口径在 6 个 service 落点一致。

**③ 安全与鉴权**
- `ProductionGuard.java`：prod/pg profile 强制 4 项 fail-fast（AES/JWT 密钥非默认、DS 须 PostgreSQL、seed 必须关闭）；非 prod 时默认密钥输出强告警（L54-64）。**默认密钥绝非裸奔，已闭环。**
- `AuthInterceptor`：每请求 traceId、X-Token+Cookie 双取令牌、跨站写 Origin 校验、401/403 拒绝。
- `SecurityHeadersFilter`：CSP 收紧（禁 object/跨源 connect）+ X-Content-Type-Options/X-Frame-Options/Referrer-Policy。
- `AesCrypto`（AES-GCM+随机IV）、登录失败锁定 5 次/15 分钟。
- `RevocationStore` 接口化，`JpaRevocationStore` 为生产默认（重启保留、可多实例共享），Redis 可实现接口扩展不伤调用方。

**④ 统计与排名 — `StatisticsService.java` / `RankingService.java`**
- 拆分为门面 + Ranking/Trend/Comparison/StatQuerySupport/StatMath 五件套，消除上帝类、行为零改动。
- 统计口径注释详尽（及格=满分×60%、优秀×85%、得分率换算兼顾不同满分）——防遗忘。
- 隐私档位三态（full/limited/aggregate 默认本人+班级聚合），P0 修复注释清晰（家长排名按归属校过滤，杜绝跨校名次混入）。
- **性能短板**：`DataScopeService.filterGradeRowsByClass`（L114-127）为内存过滤（虽统计热路径已 SQL 下压，此方法为低效残留）；`buildRankedRows/classAggregate/support.courseById` 等以内存计算为主，数据量增大时（校级数千学生）存在性能天花板。

**⑤ 前端（前端专家证据）**
- 安全性高（90）：颜色语义已修正、CSP 收紧配合到位。
- 缺口：`studentApi.list({size:1000})` 在 4 处散落——**学生超千静默截断（最高数据正确性风险）**；App.vue 侧栏写死 220px、多 el-dialog px 溢出（响应式缺口）；Login/Dashboard 缺 loading、多处空 catch、缺空态、401 重复提示、el-radio 废弃 label、颜色令牌散落。

**⑥ 测试与部署**
- 13 测试类 80 用例：覆盖鉴权流/锁定/密码加固、切换校、多租户 A/B 阶段、加密绑定、读范围守卫、家长隐私、校级多租户、统计口径、成绩服务、设置分析——多租户与安全回归覆盖强。
- 测试均为 `@SpringBootTest + @Transactional` 回滚，干净无污染；含中文方法名表述清晰。
- 部署：`publish.ps1` 三层核对（前端入 jar/后端 jar/启动器 exe）+ 零依赖 JRE(49.3MB) + launcher TLS1.2 兜底 + 端口 smoke test → 可复现、零 Java 依赖。

## 四、问题清单及优先级排名

### P1（建议尽快修复，影响数据正确性 / 稳定性）

| # | 问题 | 位置 | 影响 | 建议 |
|---|---|---|---|---|
| 1 | **学生列表 size:1000 静默截断**（数据正确性最高风险） | 前端 4 处 `studentApi.list({size:1000})` | 学生超千时列表/下拉被静默截断，家长绑定、老师选人可能漏选 | 后端切分页返回总数或前端分页/虚拟滚动；至少返回 total 并提示「已截断」 |
| 2 | 家长排名路径逐绑定 `findById`（N+1） | `RankingService.resolveParentSchoolId`（L246） | 绑定学生多时产生 N+1 查询，家长端开榜变慢 | 改用 `findByStudentIdIn` 一次性取，批量解析归属校 |
| 3 | 统计/排名内存计算为主 | `DataScopeService.filterGradeRowsByClass`、`buildRankedRows/classAggregate` | 校级数千学生时 CPU/内存突增，响应变慢 | 排名/聚合尽量 SQL 下压（`row_number`/JOIN 聚合），移除低效内存过滤残留 |

### P2（建议后续迭代打磨）

| # | 问题 | 位置 | 建议 |
|---|---|---|---|
| 4 | 非 prod 默认密钥仍可运行 | `application.yml` / `ProductionGuard` | 已闭环不阻断；交付生产包前注入 `APP_SECURITY_TOKEN_SECRET`/`APP_CRYPTO_KEY`（文档已提示） |
| 5 | 前端响应式缺口 | App.vue 侧栏写死 220px、多 el-dialog px 溢出 | 改 rem/自适应断点 |
| 6 | 前端空 loading/空态/异常处理不统一 | Login/Dashboard、多处空 catch | 抽全局反馈组件（ElMessage 收敛）、统一 loading 与 empty 状态 |
| 7 | 401 重复提示、el-radio 废弃 label、颜色令牌散落 | 全局 | 收敛为单一拦截器 + 设计令牌（CSS 变量） |
| 8 | `List<Object[]>` 手工取列魔法序号 | GradeRepository 多条 JPQL、RankingService `r[0..5]` | 引入投影 DTO/record，减少列序笔误风险（首轮 D1 系同类） |
| 9 | 前端敏感字段直出（fatherPhone/motherPhone 明文） | Student 实体 | 评估列表/详情是否需要明文手机号；如需更严可加 `@JsonIgnore` + 独立 DTO |
| 10 | JPA `ddl-auto:update` 依赖实体注解建表、无 Flyway | application.yml + V1-V4 手工脚本 | 生产建议接 Flyway/CustomMigration 保证脚本顺序可审；至少把 V1-V4 纳入发布制品清单 |

## 五、改进建议（按优先级落地）

1. **（P1-1）根治前端 size:1000 截断**：后端 `StudentRepository.search` 返回 `Page` 已具备 total；前端改为分页拉取或至少展示「共 N 人，已展示前 1000」提示，杜绝静默漏数据。
2. **（P1-2/P1-3）性能 SQL 化**：家长归属校解析改批量取数；排名/聚合优先数据库侧运算，移除 `filterGradeRowsByClass` 内存过滤残留（该路径已无 SQL 调用方时可直接删除）。
3. **（P2）前端工程化收敛**：抽全局 loading/empty/反馈组件，修复响应式与 401 重复提示，收拢颜色令牌——一次到位可显著提升 UI 可维护得分。
4. **（P2）查询结果投影化**：将 `List<Object[]>` 手工列序改为 DTO/record 投影，配合编译期类型校验，降低维护回归。
5. **（P2）生产数据迁移正规化**：将 V1-V4 SQL 纳入可执行清单或引入迁移工具，避免人工执行顺序错漏；发布制品打包时校验脚本完整。

## 六、结论

系统已完成三批遗留全闭环、80 项测试全绿、V3/V4 物理外键与 admin true-global 已落两个真实库并实测生效（24 外键拦截孤儿插入）。本轮逐行逐句复核确认：**无 P0 阻断项**，整体 85.6 分，后端多租户/安全/数据模型达到优秀水平，前端与统计性能为相对短板。建议按「先 P1（数据正确性 + 性能 SQL 化）、后 P2（前端工程化 + 投影化 + 迁移正规化）」顺序落地打磨，即可达生产级交付标准。
