## 一、P1 级修复（必须处理）

### P1-1 学生列表 size:1000 静默截断 → 前后端配合分页
**问题**：`studentApi.list({size:1000})` 散落 4 处，学生超千台静默截断，是评审确认的最高数据正确性风险。

**改造内容**
- **后端**：`StudentRepository.search(keyword, page, size)` 本就返回 Spring Data `Page`（含 `totalElements`/`totalPages`），分页能力已具备，仅前端未使用。
- **前端**（4 视图：GradeEntry / GradeQuery / StudentTrend / Statistics）：下拉改为**远程搜索分页**（el-select `filterable remote` + 远程方法），并维护 `mergeStudentMap`（id → {studentNo, name}）反查缓存，保证已选项在分页切换后不丢失；多选/批量场景补充分页表格与 `totalElements` 兼容。`StudentList.vue` 本就用真分页，未改动。
- **效果**：无论多少学生都完整拉取，杜绝静默漏数据，且规避超千量一次性渲染的性能问题。

### P1-2 家长排名路径逐绑定 findById（N+1）→ 批量查询
**问题**：`RankingService.resolveParentSchoolId` 逐条 `findById(studentId)`（每绑定一次 DB 往返）；`ParentService.claimStudent`（认领合并低频路径）存在同类 N+1。

**改造内容**
- `StudentRepository` 新增显式 `@Query` 批量方法 `findStudentsByIdsAndNotDeleted(Collection<Long>)`，一次取回全部绑定学生并按 `id→Student` 建 Map。
- `RankingService.resolveParentSchoolId`：先取绑定列表 → 批量取学生 → 按 schoolId 分组判断同校/跨校，一次往返替代逐条。
- `ParentService.claimStudent`：批量取家长名下全部绑定学生替代循环内逐条 findById。
- **踩坑记录**：初版用方法名派生 `findByStudentIdInAndDeletedFalse`，因 `Student` 实体无 `studentId` 属性，Spring Data 把 `StudentIdIn` 当嵌套属性解析，导致启动失败（80 用例全 Errors 的根因）。改为显式 `@Query` 后 80/80 全绿。

### P1-3 统计与排名 → SQL 下压，移除内存过滤残留
**问题**：排名/对比/进步在 `DataScopeService.filterGradeRowsByClass` 对 `Object[]` 全量拉取后内存过滤，班级粒度大时低效。

**改造内容**
- `GradeRepository` 新增两个 SQL 下压查询：
  - `rankRowsByClassIds(examId, courseId, source, classIds)`：排名的班域收敛直接由数据库过滤（省去全量拉取）。
  - `courseRowsByExamByClassIds(courseId, source, classIds)`：跨考试对比/进步的班域收敛同样下压。
- `TrendService.progress`：visible 非空时改用下压查询，不再内存过滤。
- `ComparisonService.comparison`（含 `semesterRows` 方法签名增加 visible 参数）：班域收敛场景走下压查询。
- `RankingService.ranking` 老师分支：visible 非空时改用 `rankRowsByClassIds`，跳过后置内存过滤。
- **删除 `DataScopeService.filterGradeRowsByClass` 内存过滤残留**（已无任何调用者；同步清理悬空 Javadoc 与未用 import `ArrayList`/`HashSet`）。
- `courseStats` 已用 `scoresByClass/statsByClass`（本就 SQL 下压），不受影响。

## 二、P2 级优化

### P2-1 非生产默认密钥随机化 + 持久化
**问题**：非 prod 环境 JWT/AES 回退**固定默认值**（`local-demo-secret-...` / `DEMO_KEY`），虽非生产可用，但规律性强、存在被利用的潜在风险。

**方案（关键权衡）**：AES 加密的**身份证号已持久化在库中**，密钥若「每次随机」会导致重启后无法解密历史数据——因此不能简单随机。正确做法为**首次启动生成强随机密钥并落盘到密钥文件、后续复用**：

- 新增 `AppKeyProvider`（config 组件），统一为 JWT 与 AES 提供密钥，优先级：**显式环境变量注入 > 本地持久化密钥文件**（首次用 `SecureRandom` 自动生成并落盘 `backend/data/app-secrets.properties`，后续复用；文件权限仅本机）。
- `JwtUtil` / `AesCrypto` 改为注入 `AppKeyProvider`（保持既有构造兼容性，以 `@Value` 兜底）；移除 `AesCrypto` 的固定 `DEMO_KEY` 与未使用的 `padKey`。
- `ProductionGuard` 改用 `AppKeyProvider.isJwtExplicit/isAesExplicit`：非 prod 仅在「完全未注入且未持久化」时提醒公网部署需注入；**生产 fail-fast 语义保持不变**（仍强制显式注入 + PostgreSQL + 关闭 seed）。
- `application.yml` 的 `token-secret` 默认值改为空（不再写死 Demo 字面量），避免覆盖 provider 随机值。
- **实证**：smoke 启动日志输出 `[APP-KEY] JWT=本地随机持久化，AES=本地随机持久化；未注入方已使用本地持久化随机密钥文件（首次自动生成）`；密钥文件 `backend/data/app-secrets.properties` 已生成。

### P2 其余优化（前端专家落地 + 联调）
- **前端响应式**：`App.vue` 侧栏由写死 220px 改为 `collapsed` 折叠变量 + `asideWidth` computed（折叠后 64px）+ 媒体查询兜底 + 窄屏适配。
- **el-dialog 溢出**：多处 `px` 溢出修复，窄屏下不挤压。
- **loading 空态**：`Dashboard.vue` / `Login.vue` 补 loading；多视图空态补齐。
- **401 防重复提示**：`http.js` 统一 401 跳转，避免重复弹窗。
- **提交防重**：表单提交重复点击防护。
- **颜色令牌、el-radio 废弃 label** 等清理。
- 以上均已通过前端构建验证。

## 五、风险与后续
- **部署注意**：`backend/data/app-secrets.properties` 是密钥持久化文件，部署/备份时须一并保留（首次在目标机启动也会自动生成；若更换机器且未保留旧文件，历史加密身份证将无法解密——需在部署时整体拷贝该文件）。
- **生产**：仍强制显式注入 `APP_SECURITY_TOKEN_SECRET` 与 `APP_CRYPTO_KEY`，ProductionGuard fail-fast 语义不变。
- **遗留 P2 项**：V1–V4 迁移正规化（接入 Flyway 或统一迁移执行入口）、敏感字段直出返回评估、`Object[]` 魔法列序进一步 DTO 化等，建议纳入后续迭代。
