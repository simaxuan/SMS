## 二、多租户数据模型与隔离（核心）

### 2.1 【P1 越权】老师**读路径**班级域过滤不一致

- 证据（对比）：
  - **有过滤**：`StatisticsService.ranking` 老师分支 `visibleClassIds` 过滤（`StatisticsService.java:462-471`）；`comparison` 走 `filterGradeRowsByClass`（`StatisticsService.java:300-305`）；写操作均有 `ensureTeacherClassScope`（`GradeService.java:176-183`）。
  - **无过滤（门敞开）**：
    - `GradeService.list` 老师分支直接 `return gradeRepository.search("teacher", examId, courseId, studentId)`（`GradeService.java:41-43`）——**CLASS 老师可看全校老师成绩**。
    - `StatisticsService.studentMultiSubject`（`StatisticsService.java:151-155`）、`studentTrend`（`StatisticsService.java:738-741`）走 `visibleGrades`，其老师分支 `findByStudentId(studentId)` 全部 teacher 返回、**不校验目标学生是否在老师可见班级**（`StatisticsService.java:845-849`）——**老师可传任意 studentId 看任意学生多科/历史成绩**。
    - `courseStats`（`StatisticsService.java:85-86`）只判角色不限班级——可看全校某科统计（聚合值，泄露有限）。
    - `progress`（`StatisticsService.java:608-610`）限角色不按班级过滤——可看全校进步/退步榜。
- 判断：读路径越权是本期最重要的隐患。`ranking`/`comparison` 已闭环节点（批次2 I-3 只覆盖了这两处），但 `list / studentMultiSubject / studentTrend / courseStats / progress` 未同步应用 `visibleClassIds`，**未分班对 CLASS 老师本应不可见（DataScopeService:88 语义），这里却全文可见**。
- 改进（P1，逐点）：
  1. `GradeService.list`：老师分支先 `dataScopeService.visibleClassIds(user)`，为 null（ALL）放行，否则仅保留命中班级学生成绩——建议下沉为带 `classIds` 集合的查询或先取可见 studentIds 再过滤。
  2. `visibleGrades` 老师分支：先解析目标学生 `classId`，用 `canManageClass(user, classId)` 校验，不可见抛 403。
  3. `courseStats`/`progress`：复用 `filterGradeRowsByClass` 或 `visibleClassIds` 收敛到可见班级。
  4. 为 CLASS=无绑定班级老师统一 `requireAnyVisibleClass` 前置（`DataScopeService.java:95-102` 已提供但未在以上读路径调用）。
  5. 补充测试：CLASS 老师查非本人班级 studentId 的 `student-trend`/`student`/`grade/list` 应 403/为空。
- 优先级：**P1（上线前修）**

### 2.2 数据模型：Grade 无冗余推导合理，但需文档化性能代价

- 证据：`DataScopeService.java:24` 明确 Grade 无 classId/schoolId 冗余，范围过滤基于 Student（join 后才有）。
- 判断：一致性好（单一数据源、无脏冗余），代价是过滤需 join Student，且部分查询（如 `findByStudentIdInAndSource` 家长路径）即便不 join 也正确。
- 改进（P2）：`rankRows`/`stats`/`scores` 等已 join Student 取 classId，性能可接受；但**所有读路径过滤必须统一收敛**（见 2.1），避免因"join 拿到 classId 后未过滤"而越权。可考虑对高频过滤字段在 Grade 冗余 `class_id`（建立 `idx_grade_class`）以提升排名/统计性能，同时用触发器/JPA 维护一致性（属批次4范围）。

### 2.3 跨校绑定一致性（I-4）已闭环

## 三、核心业务逻辑正确性

### 3.1 AuthService：锁定可被「用户名/手机号双通道」部分绕过 + 内存态

- 证据：
  - `findByLoginName` 先按 username 再按 phone（`AuthService.java:95-99`），但 `failCounter` 以 `req.getUsername()` 作键（`AuthService.java:69`）。
  - 同一账号既有 `username` 又有唯一 `phone`（`Account.java:14-15` uk_account_phone）。攻击者可用 **username 错 5 次 + 手机号再错 5 次** 交替，绕过「5 次/15 分钟」锁定（两个键各自计数）。
- 判断：锁定键应归一化到**账号唯一标识**（accountId），而非登录输入串。
- 改进（P1）：
  1. 先解析出 `accountId`（成功或失败时由库返回），用 `accountId` 作锁键；或锁定前先 `findByLoginName` 拿到账号。
  2. 锁定状态当前在内存（重启清零），多实例各自计数——标注为单机方案，分布式需 Redis（批次5）。
- 优先级：P1

### 3.2 标准分多模式与统计口径正确

- 证据：`weightedStdScore`（`StatisticsService.java:218-243`）三模式实现、`parseStdWeights` 解析失败回退 equal、定制满分成绩用得分率归一（`StatisticsService.java:177-178`）。
- 判断：实现正确且注释完备，`StatisticsMetricTest` 有覆盖。
- 优先级：无需改

### 3.3 ParentService 认领迁移存在「跨自建生误迁」边界

- 证据：`claimStudent` 遍历家长名下**所有** self 学生并调 `migrateSelfGrades(mine, sch)`（`ParentService.java:216-225`）；`migrateSelfGrades` 把 `mine` 的 parent 成绩改挂到 `sch`（`ParentService.java:241-253`）。
- 判断：若家长建了**多个**自建学生（同名不同学号分别自测），认领一个校园生时会把**全部**自建生的历史成绩都迁移过去，可能张冠李戴；目前无绑定校验该自建生与目标校园生是否为同一人（仅靠姓名+学号+身份证在 `claimStudent` 头部的单次匹配，无法区分多个 self）。
- 改进（P2）：
  1. 迁移前增强校验：仅当自建生与目标校园生**出生日期/身份证一致（可解密的 idCard 全量比对）或学号一致**才迁移。
  2. 提供迁移确认/回滚语义（当前**不回滚父级**且 `merged=true` 后不可恢复）。
- 优先级：P2

### 3.4 并发唯一冲突兜底正确

- 证据：`GradeService.create` 捕获 `DataIntegrityViolationException` → 409（`GradeService.java:82-87`）；`batchCreate` 捕获后跳过（`GradeService.java:148-150`）。

- 改进（P3）：`batchCreate` 对超满分行 `continue`（`GradeService.java:140-142`）静默跳过，建议记录跳过明细并给前端提示条数。

## 五、安全

### 5.1 【P1/P2】AES 使用 ECB 模式 + 默认密钥风险

- 证据：`AesCrypto.java:45` `AES/ECB/PKCS5Padding`；默认密钥硬编码（`AesCrypto.java:19-20`），仅当 `APP_CRYPTO_KEY` 存在才覆盖；`DataSeeder` 直接 `new AesCrypto()`（`DataSeeder.java:167`，用默认密钥加密演示身份证）。
- 判断：
  1. **ECB 不安全**：相同明文块产生相同密文，身份证（18 位定长、结构规律）易被分析出模式，属加密模式选型缺陷。
  2. **默认密钥可被用于生产**：若生产未注入 `APP_CRYPTO_KEY`，一律用公开的硬编码 key，身份证等同明文。
  3. `DataSeeder` 里 `new AesCrypto()` 与注入的单例 `AesCrypto` **可能使用不同密钥**（依赖环境变量读取时机），导致种子的 idCard 用默认 key 加密、运行时用注入 key 解密失败——存在潜在不一致。
- 改进（P1）：
  1. 改用 **AES/GCM/NoPadding**（带随机 IV/Nonce）替换 ECB。
  2. 移除 `new AesCrypto()`，统一通过容器注入同一个实例；`DataSeeder` 只接受已注入的 `AesCrypto`。
  3. 启动时强制校验：当 `app.seed.enabled` 或加密启用且未设 `APP_CRYPTO_KEY` 时，生产 profile 直接拒绝启动（fail-fast），而非静默用默认 key。
- 优先级：**P1（改 GCM）+ P2（默认 key fail-fast）**

### 5.2 会话安全纵深已成型，但内存态在多实例下失效

- 证据：Cookie HttpOnly+SameSite=Lax（`AuthController.java:70-74`）、`AuthInterceptor` 全局安全头 + CSRF Origin 兜底 + OPTIONS 放行（`AuthInterceptor.java:41-59`）、`JwtUtil` 验签/过期/版本/黑名单四重校验。
- 判断：单实例正确。但 `denylist`/`tokenVersions` 在 **多实例**（负载均衡）下各自独立，登出/改密只在该实例生效；应用重启则全部失效（安全让步可用性，方向安全侧）。
- 改进（P2，注明为批次5）：
  1. 分布式部署需将 tokenVersions（改密失效）与登出黑名单迁移到 Redis（带 TTL），failCounter 亦同。
  2. 单机部署可接受现状，但 README 需明确「单实例部署假设」。
- 优先级：P2（现单实例无需阻塞上线）

### 5.3 公网强约束已写入审批，需落实为机制

- 证据：`application.yml:26-30` 密钥默认值 + 注释强提醒；`AuthController` 未强制 Secure。
- 判断：代码层面无法强制 HTTPS，靠部署纪律。
- 改进（P2）：提供 `application-prod.yml` profile：数据源→PG、ddl-auto→validate/none、seed 关闭、H2 console 关闭、CSP 收紧；并配套启动校验（见 5.1.3）。
- 优先级：P2
