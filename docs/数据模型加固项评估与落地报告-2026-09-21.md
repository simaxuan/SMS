> 版本：v1.0 ｜ 日期：2026-09-21 ｜ 主题：组织关联整改后的数据模型加固项「重新评估 + 最优方案落地」

## 一、背景与范围

上一轮组织关联整改（修复超管识别缺陷 + 前端挂接）已落地并通过构建验证。本轮按用户指令，对**有意暂缓的数据模型加固项**重新分析评估，提供推荐方案，并按最优方案执行。

评估过程中**新发现上轮遗漏的同源缺陷**（`currentSchoolId()` 兜底遗漏），一并纳入本轮落地。

## 三、三项数据模型加固项逐项评估

### 3.1 加固项①：`grade.school_id` 非空约束

**现状（已核实源码）**：
- 实体 `Grade.java`：`school_id` 为可空冗余快照，已有 `idx_grade_school` 索引；字段注释明确「八轮强约束，自建学生成绩可空」。
- 写路径**已完整回填**：`GradeService.create(L258)/update(L137-138)/batchCreate(经 toEntity L258)` 均通过 `studentRepository.findByIdAndDeletedFalse(...).ifPresent(s -> g.setSchoolId(s.getSchoolId()))` 从所属学生回填。
- 查询已按校过滤（读路径兜底见第 4 项修复）。

**风险分析**：
- 强制 `school_id` 非空会与「自建学生成绩可空」语义冲突——自建学生（家长自定义小测场景）可能无归属校，加非空约束将拒绝合法写入。
- 写路径已保证隔离正确性，加约束不增加实际安全收益，反而引入数据写入阻塞风险。
- 历史库已有 `school_id IS NULL` 数据，加非空需要先回填迁移，成本高于收益。

**结论**：**维持可空 + 已有索引**即为最优。隔离正确性依赖写路径回填（已完整）+ 读路径过滤（本轮修复），不依赖列级非空约束。**暂缓，不加约束、不做历史回填**。

### 3.2 加固项②：`teacher_class` 增加 `school_id` 冗余列

**现状（已核实源码）**：
- `TeacherClass.java`：仅 `teacher_account_id + class_id`（唯一键 `uk_teacher_class`），另建 `idx_tc_class` 索引。
- 老师归属学校/级部均为**间接**：`teacher_class.class_id → class.school_id / class.level_id`，通过 join Class 得出。

**是否需要冗余列**：
- 冗余列的用途是简化「某校/某级部全部老师」查询，避免每次 join。
- 当前查询量小，`idx_tc_class` 已覆盖按班/按老师到班的常用路径；「某校全部老师」走 join Class 一次即可，无性能瓶颈。
- 冗余列引入**双写一致性风险**（class 改校/级部时需要同步 teacher_class 冗余列），维护成本高于收益。

**结论**：**不需要**。维持间接关联（`teacher_class → class`）为当前正确数据模型，配合 `idx_tc_class` 索引已满足查询需求。**不做冗余列**。

### 3.3 加固项③：新建 `teacher_level` 老师-级部直接关系表

**现状产品语义**：
- 老师↔级部为**间接归属**（`teacher_class → class.level_id`）：老师绑到具体班级，班级归属级部，从而老师间接挂到级部，天然支持跨级（一人绑多班跨多个级部）。
- v5 定稿老师默认 CLASS，可绑多班、可跨级。

**是否建直接关系表**：
- `teacher_level` 直接表会让老师「直接指定级部」，与现有「通过班级间接归属」形成**两套并存、易产生歧义**的数据源——老师到底归属哪个级部，取决于查 teacher_class 还是 teacher_level。
- 本期产品语义并无「老师直挂级部而非挂班级」的强需求，属于**功能增强**而非缺陷修复。
- 新增表涉及建表 + 迁移 + 前端交互（老师需先选级部再选班）+ 双数据源一致性治理，工作量大且动到字段规范基线。

**结论**：**不建议**。本期维持「间接归属」语义，`teacher_level` 列为后续产品增强的独立立项候选，不纳入本次数据模型加固。

## 四、落地的最优修复（缺陷项）

### 4.1 根因回顾

`DataScopeService.currentSchoolId()` 仅以 `u.getSchoolId()` 取值，**不区分超管**。而 `DataSeeder` 给 admin 设了**非空 schoolId（演示学校）**（SCOPE_ALL 超管被误当演示学校归属用户）。上一轮已修复写路径与 `schoolFilterForStatistics()`，但**读路径 `currentSchoolId()` 兜底仍有遗漏**，导致超管被锁在演示学校。

### 4.2 本轮落地清单

| 文件 | 修改 | 说明 |
|------|------|------|
| `GradeService.list` | `currentSchoolId()` → `schoolFilterForStatistics(user)` | 读路径超管放开全校（`schoolFilterForStatistics` 对 SCOPE_ALL 返回 null）|
| `ExamService.list` | `currentSchoolId()` → `isGlobalAdmin() ? null : currentSchoolId()` | 读路径超管放开全校考试 |
| `ExamRequest` | 新增 `schoolId` 字段 | 支持超管跨校建考试时显式指定 |
| `ExamService.create` | `currentSchoolId()` → `resolveWriteSchoolId(req.getSchoolId())` | 写路径超管可跨校建考试（与课程/班级对齐）|
| `DataScopeService.resolveWriteSchoolId` | SCOPE_ALL 分支：requestedSchoolId 为空时回退登录校 | 避免产出 `school_id=null` 归属，防止普通老师按校查不到 |
| `SettingsService.currentSchoolId` | 对 SCOPE_ALL 返回 null | 超管读写「全局行」而非演示学校 local 行（修复 full 档位等全局配置跨校生效问题）|
| `Exam.vue` 前端 | 超管显示「归属学校」列 + 选校下拉 | 前端配合超管跨校建考试；列表展示归属学校 |

### 4.3 修复后工作流

1. **全局超管（SCOPE_ALL）**：
   - 查成绩/查考试 → 放开全校（不再锁演示学校）；
   - 建考试/课程/班级/级部 → 可在选校下拉指定任意学校，未指定默认当前登录校；
   - 改设置（如 `parent_rank_detail=full`）→ 落全局行，全校生效。
2. **普通老师（CLASS/SCHOOL）**：锁登录校不变，读本校、写本校，隔离开放无泄露。
3. **学校隔离**：所有跨校操作均经 `resolveWriteSchoolId` 收敛，杜绝越权。

## 六、结论

- **三项数据模型加固项均评估为「暂缓/不做」**：`grade.school_id` 写路径已完整回填（非缺陷）、`teacher_class` 无需冗余列、`teacher_level` 属产品增强。三者以「维持现状 + 已落索引/写回填」即为最优，避免高风险 schema 迁移。
- **真正必要且落地的是上轮遗漏的 `currentSchoolId()` 兜底缺陷**：覆盖 GradeService/ExamService 读路径 + ExamService 写路径 + SettingsService 全局行，超管从此不再被锁演示学校，跨校管理能力与课程/班级完全对齐。
- 后端 `mvn compile`、前端 `vite build` 双通过，修复无回归。
